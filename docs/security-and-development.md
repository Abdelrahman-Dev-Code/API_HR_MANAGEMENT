# الأمان وقواعد التطوير

## المصادقة

- تستخدم API Laravel Sanctum Personal Access Tokens.
- لا ترسل token في query string.
- لا تحفظ token في Git أو ملفات logs أو screenshots.
- استخدم HTTPS خارج البيئة المحلية.
- ألغِ token عند logout.
- غيّر كلمة مرور admin التجريبية قبل الإنتاج.

## التفويض

`auth:sanctum` يثبت هوية المستخدم، ثم تطبق Gates صلاحيات الموارد على المسارات. المستودعات ونقاط الكتابة تحصر الموارد الحساسة بحسب `hr_admin` أو قسم مدير القسم أو سجل الموظف المرتبط بالحساب.

أمثلة على التفويض المتوقع:

- الموظف العادي يقرأ بياناته فقط.
- HR يدير الموظفين والإجازات.
- Payroll يدير الرواتب.
- Admin يدير الأدوار والصلاحيات.

تستخدم Form Requests للتحقق من المدخلات، بينما التفويض العام موجود في route middleware وGates. راجع توزيع الأدوار الفعلي؛ دور `department_manager` يحتاج ملف موظف بقسم صحيح، ولا يمنح صلاحيات اعتماد الإجازة أو الراتب تلقائيًا. المؤسسة محمية بـ Gate `manage-organization` وصلاحية `organization.manage` من دور فعال.

## التحقق

- استخدم `$request->validated()` فقط.
- لا تستخدم `$request->all()` في عمليات الحفظ.
- تحقق من IDs عبر `exists`.
- تحقق من unique fields عبر `Rule::unique` مع `ignore` عند التحديث.
- ملفات المستندات تتحقق من النوع والحجم قبل التخزين، وتبقى على disk خاص ولا تُنشر عبر `storage:link`.

## تنظيف مدخلات FormRequest

كل Form Requests ترث من `App\Http\Requests\SanitizingFormRequest`، الذي يطبّق قبل validation:

- إزالة null bytes ومحارف التحكم غير المرئية.
- إزالة HTML tags من النصوص وقص المسافات الخارجية.
- معالجة عناصر المصفوفات بشكل متكرر.
- إبقاء كلمات المرور والتوكنات دون تعديل.

هذا التنظيف لا يستبدل validation، ولا يمنع SQL injection وحده؛ Eloquent parameter binding هو المسؤول عن الاستعلامات الآمنة. كما يجب دائمًا استخدام `{{ }}` في Blade أو ترميز النص حسب سياق الواجهة؛ لا تعتبر `strip_tags` بديلًا عن output encoding.

## Mass Assignment

Models تستخدم `Fillable` Attribute لتحديد الحقول القابلة للتعبئة. عند إضافة حقل حساس، لا تضفه إلى fillable دون سبب.

## كلمات المرور

`User` يستخدم cast:

```php
'password' => 'hashed'
```

ولا يجب تخزين كلمات مرور صريحة في قاعدة البيانات. كلمة مرور Seeder التجريبية استثناء محلي يجب تغييره.

## البيانات التاريخية

نظام HR يحتوي حضورًا ورواتب ومستندات تاريخية. انتبه إلى `cascadeOnDelete`؛ حذف الموظف فعليًا قد يحذف التاريخ التابع. الأفضل في الإنتاج تعطيل الحذف الفعلي أو اعتماد سياسة أرشفة واضحة.

## الوردية الليلية

- استخدم `check_in_at` و`check_out_at` كتاريخ ووقت كاملين.
- `attendance_date` يمثل تاريخ بداية الوردية.
- لا تعتمد على `TIME` فقط في حساب وردية تعبر منتصف الليل.
- القيد الفريد هو `employee_id + attendance_date + shift`.

## الإجازات

يجب تنفيذ التالي في Service أو Action مع transaction:

1. منع تداخل إجازتين معتمدتين لنفس الموظف.
2. حساب `total_days` وفق سياسة نهاية الأسبوع.
3. منع تجاوز `used_days` للرصيد.
4. تحديث الرصيد عند اعتماد الإجازة فقط.
5. تسجيل من اعتمد الطلب في `approved_by`.

## الرواتب

- لا تثق بقيمة `net_amount` المرسلة من العميل؛ احسبها على الخادم.
- افصل حالة الموافقة عن حالة الدفع إذا احتاج النظام ذلك.
- لا تحذف تاريخ الرواتب مع حذف موظف في نظام إنتاجي.
- احتفظ بعملة وفترة وقواعد الحساب إذا كان التدقيق المالي مطلوبًا.

## قاعدة البيانات

- لا تعدل migration نفذت في production.
- أنشئ migration جديدة للإصلاحات.
- اختبر MySQL الفعلي، خصوصًا JSON وforeign keys.
- الاختبارات تستخدم SQLite in-memory افتراضيًا؛ اختبر على MySQL قبل الإنتاج، خصوصًا المعاملات والأقفال والتزامن.
- استخدم indexes في migration عند وجود استعلامات متكررة.
- راجع سياسة soft delete والـ unique fields قبل السماح بإعادة استخدام الأكواد.

## الأداء

- استخدم eager loading في Repository عند الحاجة.
- لا تعمل queries داخل Blade أو Resource بطريقة غير محسوبة.
- استخدم pagination للقوائم.
- تجنب تحميل كل الموظفين أو الحضور دفعة واحدة.
- استخدم `withCount` أو aggregates عند عرض العدادات.

- token محمي ومفقود.
- validation 422.
- uniqueness عند الإنشاء والتحديث.
- إنشاء وتحديث وحذف الموارد.
- الوردية الليلية عبر منتصف الليل.
- منع تداخل الإجازات وتجاوز الرصيد.
